# 终端用户 ID 请求头

部分上游渠道支持在请求头中携带终端用户 ID（通用头名 `X-End-User`）。渠道据此把策略拒绝归因到具体终端用户，只封禁该用户，而不是暂停整个 API key。本功能让 sub2api 在出站请求上携带这个 ID，并支持多级 sub2api 转发。相关 Issue：#342。

## 终端用户 ID 的来源

终端用户 ID 在请求进入的第一个 sub2api 实例确定，之后逐级原样传递：

| 调用方 | 终端用户 ID |
| --- | --- |
| 普通用户的 API key | 当前 API key ID |
| 管理员用户的 API key，且请求带合法的 `X-Sub2api-End-User` | 该入站值（原样沿用，不替换成管理员 key 的 ID） |
| 管理员用户的 API key，入站值缺失或格式非法 | 当前 API key ID |

合法格式：`^[A-Za-z0-9_.:-]{1,128}$`。非管理员 key 携带的 `X-Sub2api-End-User` 一律忽略，防止调用方伪造 ID 把违规归到他人名下。因此入口实例调用号池实例时，必须使用管理员用户的 API key。

## 账号配置

账号编辑页「出站携带终端用户 ID」，对应账号 `extra` 字段：

| 字段 | 含义 |
| --- | --- |
| `end_user_header_enabled` | 开关，默认关闭 |
| `end_user_header_name` | 出站头名，留空为 `X-End-User` |
| `end_user_header_prefix` | 可选前缀（最多 32 个字符，仅限 `[A-Za-z0-9_.:-]`），出站值为 `<prefix><ID>` |

- 只有开启的账号才发出终端用户头；未开启的账号（不支持该头的渠道、OAuth / 订阅类账号等）不发出任何终端用户头。
- 入站的 `X-Sub2api-End-User` 在任何账号的出站请求中都会被剥离，不会被原样发往上游；它也不能加入客户端请求头透传白名单，不能用请求头覆写配置。
- 出站时会先删除配置头名的所有大小写形式再写入，客户端自带的同名头不会到达上游。
- 拼接前缀后超过 128 个字符时不发出该头。

## 两级转发配置示例

```
终端用户 key ──▶ 入口实例 ──管理员 key──▶ 号池实例 ──渠道账号──▶ 上游渠道
```

1. 入口实例：指向号池实例的账号开启，头名填 `X-Sub2api-End-User`。
2. 号池实例：入口实例调用时使用的 API key 必须属于管理员用户。
3. 号池实例：支持该头的渠道账号开启，头名 `X-End-User`（或渠道要求的头名）；其他账号保持关闭。

渠道反馈某个 ID 被封禁时，在入口实例上按该 key ID 定位终端用户。

### 撞号

如果号池实例同时服务多个来源，并且这些来源都走同一个渠道（例如入口实例转发来的流量和直连号池实例的用户），不同实例的 key ID 可能相同，会被渠道视为同一个用户。此时在入口实例指向号池实例的账号上配置前缀（如 `a:`）。只有一个来源时不需要配置。

## 覆盖范围

终端用户头的注入点与 `trace_id_passthrough`（`X-Trace-Id`）相同，覆盖 Anthropic Messages、OpenAI Chat Completions / Responses / Embeddings / Images、Gemini、Antigravity、Bedrock（在 SigV4 签名之前注入）等出站路径，并覆盖 OpenAI WebSocket 握手头。

WebSocket 握手头只在建连时发送一次。账号开启本功能后，连接池按终端用户 ID 分组复用连接，不同终端用户不会共用同一条已握手的连接。

## 已知取舍

- 本功能不改变并发与限流。号池实例上入口实例管理员用户的并发上限，仍需按其全部终端用户的总量配置。
- 以 API key ID 归因：终端用户换一个新 key 就会得到新的 ID。
